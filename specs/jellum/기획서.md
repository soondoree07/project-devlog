## 1. 프로젝트 개요

### 1.1 한 줄 컨셉
화면 위를 유영하는 해파리를 키우는 데스크톱 마스코트. 사용자가 지정한 작업용 앱·사이트에 집중한 시간만큼 자라고, 딴짓하면 쇠약해진다.

### 1.2 제품 정체성

단순한 데스크톱 펫이 아니라 **집중 시간을 시각화하는 도구**다.

**경쟁 상대는 데스크톱 펫이 아니라 게임화된 집중 앱이다.** 스팀에는 이미 이 카테고리가 형성돼 있고, Focus Plant(식물 키우기)·PacaPomo(알파카 키우기)는 컨셉이 Jellum과 거의 같다.

**그 안에서 Jellum의 차별점은 자동 판정이다.** 비교군 다섯 제품이 전부 수동 타이머다. 사용자가 "시작"을 누르고 25분을 잰다. **앱·사이트를 자동으로 판정해 집중을 측정하는 제품은 없다.** 4장 전체가 이 카테고리에서 유일한 기능이다.

> **유료 근거:** "집중 시스템"이 아니라 **"버튼을 안 눌러도 되는 집중 측정"**이다.

### 1.3 타겟
- 재택 근무자, 학생, 프리랜서
- 뽀모도로·집중 앱을 써봤지만 매번 타이머를 눌러야 하는 게 번거롭거나, 숫자만 보는 게 무미건조하다고 느낀 사람

### 1.4 네이밍
- **Jellum** = jelly + lumen(빛). 해파리와 발광 시스템을 동시에 담은 조어
- 한국어권에는 부제 `해파리 키우기`를 병기해 스팀 국내 검색 유입 확보
- 검토 후 탈락한 후보: Ephyra(크립토 플랫폼·iOS 앱과 충돌), Rhopalia(발음 장벽), Abyssa(심해 호러 계열로 오독), Jellow(AAC 앱 브랜드 선점)
- **도메인·상표 조회 완료 (2026-09-05).** `jellum.com`은 도메인 투자업체가 보유 중이나 `jellum.app`·`jellumapp.com` 등은 미등록. USPTO 상표·스팀 동명 게임 없음. **확보는 스팀 공개 직전에 한다.** 상세는 결정로그 6번

### 1.5 플랫폼 / 배포

## 2. 캐릭터

### 2.1 종
해파리. 선정 근거:
- 부유 이동이라 화면 위 이동이 자연스럽고 어색하지 않음
- 반투명이라 다른 창 위에 떠 있어도 시야를 크게 방해하지 않음
- 발광 표현으로 상태(집중/쇠약)를 텍스트 없이 전달 가능
- 데스크톱 펫에서 흔치 않음 (고양이·강아지·슬라임·드래곤 회피)

### 2.2 아트 방향
- 픽셀아트 아님. 일러스트 기반
- 진화는 **형태 변경이 아니라 속성 변화**로 표현
  - 갓(우산)의 크기와 두께
  - 촉수의 길이·개수·굵기
  - 투명도와 내부 무늬
  - 발광의 세기와 색
- 얕은 바다 해파리 → 심해 해파리 방향으로 갈수록 화려해짐

> **화풍 미정.** 깔끔한 반투명 발광(벡터적)이냐 수채·텍스처가 살아있는 회화체냐가 안 정해져 있고, 이게 2.3의 툴 선택을 결정한다. **두 방향 시안을 만들어 비교한 뒤 확정한다.**

### 2.3 애니메이션 방식

본 리깅 방식 사용. 모션 추가 시 원화를 다시 그리지 않아도 되므로 마스코트처럼 상태가 많은 제품에 적합.

| 후보 | 비용 | 메시 변형 | 상태 머신 | 런타임 | 유지보수 |
|---|---|---|---|---|---|
| **Spine Professional** | **$369 영구** | 포함 | 없음 (코드로 직접) | 상용, 웹 런타임 있음 | 활발 |
| DragonBones | 무료 | 포함 | 없음 | 커뮤니티 | 사실상 중단 (Egret) |
| **Rive** | 무료 티어 + 상용 출시 시 $9/월 | 포함 (무료 티어부터) | **내장** | 오픈소스·무료, 런타임 수수료 없음 | 활발 |

> **v0.2의 오류 정정.** 이전 버전은 "Spine 개인 라이선스 $69"로 적었으나 이는 Essential 등급이고 **메시·웨이트·IK가 빠져 있다.** 뼈 회전만 된다. 해파리는 갓의 수축·이완과 촉수의 흐느적거림이 핵심 모션이라 메시 변형 없이는 만들 수 없다. 실제로 필요한 등급은 **Professional $369**다.

**DragonBones는 쓰지 않는다.** 유료로 파는 상주 프로그램의 렌더링 심장부를 유지보수가 끊긴 런타임에 맡기는 위험이 크다.

**Rive가 유력한 이유는 가격이 아니라 상태 머신이다.** 7.1에 상태 10종, 7.2에 전이 규칙이 이미 그래프로 설계돼 있다. Rive는 이 그래프를 툴 안에서 만들고 앱에서는 `stress`·`stage` 같은 입력값만 던지면 된다. Spine이면 전이 로직을 전부 코드로 짜고 유지해야 하고, 여기에 5단계 × 4스트레스 변형이 곱해진다.

> **결정 대기: Spine Pro / Rive.** 갈림길은 2.2의 화풍이다. 깔끔한 반투명 발광 → Rive. 수채·텍스처 회화체 → Spine Pro.
> **주의:** 어느 쪽이든 리깅을 전제로 원화를 그려야 한다. 촉수와 갓을 레이어로 분리하고, 겹쳐 가려진 부분이 없도록 벌린 자세로 작화.

## 3. 성장 시스템

### 3.1 진화 단계

| 단계 | 도달 조건(단계별) | 도달 조건(누적) | 상태 |
|---|---|---|---|
| 1단계 | 시작 | 0일차 | 유생 |
| 2단계 | +3일 | 3일차 | |
| 3단계 | +5일 | 8일차 | |
| 4단계 | +7일 | 15일차 | |
| 5단계 | +15일 | 30일차 | 완성체 |

- 4단계 구간이 15일로 가장 길다. 이 구간이 비어 있으면 이탈하므로, **단계 내부에서도 크기·발광·촉수 길이가 눈에 띄게 연속 변화**해야 한다.
- 5단계 도달 후에도 크기는 계속 미세하게 증가 (상한 있음). "며칠째 키우는 중" 카운터를 별도 표시.

> 여기서 "일차"는 달력 날짜가 아니라 **일치(day-credit)** 단위다. 1일치 = 120 exp.

### 3.2 경험치 규칙

**집중 1분 = 1 exp.** 연속 집중 배율 없음 (잠깐 이탈했다고 배율이 날아가는 스트레스 회피).

| 구간 | 인정률 |
|---|---|
| 하루 **300분(5시간)까지** | **1:1** |
| 300분 **초과분** | **1/10** |

- **하드 상한은 없다.** 12시간을 몰아쳐도 180 exp(1.5일치)에서 자연히 멈춘다
- **1일치 = 120 exp**, 완성까지 **총 3,600 exp**
- **이 300분 기준선은 전역 고정값이다.** 사용자가 바꿀 수 없다

**사용자 설정 일일 목표(기본 120분)는 성장 계산에서 분리한다.** 목표는 "오늘 해냈다" 표시와 상태 패널 표시에만 쓴다. 학생은 목표를 60분으로 낮춰 매일 달성감을 받되, 성장 속도는 정직하게 실제 집중량을 따라간다.

**사용자 유형별 완성 기간**

| 하루 집중 | 완성 |
|---|---|
| 60분 | 60일 |
| 120분 (기본 목표) | **30일** |
| 180분 | 20일 |
| 300분 (5시간) | 12일 |
| 주말만 각 5시간 | 42일 |

> **왜 이렇게 정했나:** 앱만 켜두고 방치해도 자라면 시스템이 무의미하므로 성장은 실제 집중 시간에만 비례한다. 동시에 v0.2의 "일일 상한 1.0일치 + 부분 인정" 조합은 총 집중 시간이 같아도 편차가 큰 사용자가 구조적으로 손해를 보는 구조였다(주말형 105일). 1:1 구간을 5시간으로 넓혀 해결했다. 상세는 결정로그 3번.

### 3.3 먹이 — 집중의 시각화

집중하는 동안 화면 위쪽에서 작은 먹이가 천천히 내려오고, 해파리가 그것을 먹으러 간다.

**먹이는 exp 를 주지 않는다.** 이유가 셋이다.

- 3.2 의 규칙(하루 300분까지 1:1, 총 3,600 exp)이 성장의 유일한 근거다. 먹이가 exp 를 더하면 이 계산이 통째로 깨진다
- exp 를 먹이에 담아 보내면 **화면이 가려진 동안 유실된다.** 전체화면으로 논문을 읽고 전체화면 IDE 로 코딩하는, 가장 깊게 집중하는 사용자가 가장 손해를 본다. 5.1 의 "쌓은 것을 잃게 하지 않는다"에 정면으로 걸린다
- 그래서 **exp 는 시간에 붙이고 먹이는 그 적립을 눈에 보이게 하는 장치로 둔다.** 먹는 순간 `+N` 을 띄워 방금 쌓인 양을 보여준다

이렇게 두면 먹이가 곧 **"지금 집중이 쌓이고 있다"는 증거**가 된다. 1.2 가 정한 제품 정체성 — 집중 시간을 시각화하는 도구 — 와 정확히 맞는다.

#### 나타나는 조건 — 셋을 모두 만족할 때만

1. **해파리가 화면에 있다** — 7.3 의 `front` 또는 `behind`. `hidden` 이면 나오지 않는다
2. **해파리가 깨어 있다** — 수면 상태가 아니다
3. **집중 중이다** — 지금 판정이 긍정이다

셋 중 하나라도 깨지면 **떨어지던 먹이도 즉시 거둔다.** 화면이 보이는 상태에서 사라질 때만 200ms 로 흐려지며 없어진다. 가려진 상태면 어차피 안 보이므로 바로 없앤다.

> 이 규칙 하나로 전체화면 전환·트레이 숨김·자리 비움·모니터 분리·절전 복귀가 전부 같은 방식으로 처리된다. 예외를 여섯 군데 흩어 놓지 않는다.

#### 해파리가 마중 나간다

**떨어지길 기다리지 않는다.** 처음엔 잡을 지점을 미리 정하고 먹이 속도를 역산해 해파리가 거기서 기다리게 했는데, 기다리는 모습이 굼떠 보였다.

지금은 **먹이가 일정한 속도로 내려오고 해파리가 가까운 것부터 쫓아가 먹는다.** 화면 위쪽에 나타나면 해파리가 위로 헤엄쳐 올라가 마중 나간다. 속도를 맞출 일이 없어져 코드도 단순해졌다.

**놓치지 않는 장치는 하나 남는다** — 부유선(화면 세로 80%)에 닿으면 멈추고 그 자리에 떠서 기다린다. 해파리가 다른 먹이를 먹느라 늦어도 사라지지 않는다. 바닷속 먹이가 중성부력으로 떠 있는 것이라 어색하지도 않다.

| 항목 | 값 |
|---|---|
| 평소 유영 | **20 px/s** |
| 추격 | **38 px/s** (평소의 1.9배) |
| 낙하 | **6~15 px/s** — 먹이마다 하나 골라 끝까지 유지 |
| 한 무리 | 3개, 1.4초 터울, 퍼지는 폭 520px |

속도는 세 번 낮췄다. 유영 34 → 20, 추격 100 → 60 → 38, 낙하 54 → 16~42 → 10~26 → 6~15. 화면에서 볼 때마다 빨랐다. 해파리는 빨리 다니는 생물이 아니고, **느릴수록 갓의 박자가 눈에 들어온다.**

#### 어디에 떨어지나

**주 모니터에만 떨어진다.** 해파리는 모니터를 자유로이 다니지만(7.3), 위쪽 모니터에서 먹이가 내려오면 사용자가 보고 있지 않은 화면에서 벌어지는 일이 된다.

**자리는 무작위다.** 다만 한 무리가 퍼지는 폭은 520px 로 묶는다.

```
  ① 화면 어디든 무작위로 폭 520px 짜리 띠를 하나 고른다
  ② 그 띠 안에서 셋의 가로 위치를 각각 무작위로 뽑는다
  ③ 오버레이(Overwolf 등)가 차지한 자리는 피한다
```

**띠 폭을 묶는 이유는 메모리다.** 셋을 화면 전역에 흩으면 먹이 창이 1292px 까지 넓어지고, 투명 창의 GPU 합성 부담으로 상주 메모리가 135MB 를 찍는다. 띠로 묶으면 창이 300px 안쪽으로 유지되고 130MB 안에 들어온다. (9.1)

#### 나머지 규칙

- **주기** — **집중 30초마다 한 무리(3개)**. 하나씩 1.4초 터울로 놓는다. 처음엔 3분으로 잡았는데 너무 뜸했다. 잦으면 산만하고 뜸하면 잊히므로 플레이테스트로 조정한다. **한 번에 한 무리만 존재한다** — 쫓는 도중에 다음 무리가 겹쳐 나오지 않고, 다 먹은 순간 주기를 다시 세므로 밀린 먹이가 몰려나오지도 않는다
- **먹는 순서** — 해파리는 **가장 가까운 것**부터 먹으러 간다. 대열을 지어 내려오지 않으므로 순서가 매번 다르다
- **자리** — 주 모니터에만 떨어진다 (위 "어디에 떨어지나" 참조)
- **먹는 판정** — 갓 중심과 먹이 사이 거리가 `갓 반지름 + 먹이 반지름 + 여유` 안이면 먹는다. 창 한가운데가 아니라 **갓**이 기준이다 — 렌더러가 촉수 자리를 남기려고 갓을 위쪽에 그린다
- **모양** — 작고 흰 알갱이에 노란빛이 돈다. 해파리의 청록 발광과 대비돼 눈에 띈다. **크기는 고정이고 둘레의 빛만 반짝인다** — 알갱이가 커졌다 작아지면 거리감이 흔들려 보인다
- **창** — 먹이 전용 작은 창을 따로 띄운다. 해파리 창을 화면 전체로 키우면 캔버스만 8MB 에 전체화면 투명창 합성 부담까지 생겨 9.1 의 메모리 예산이 위험하다
- **로직은 메인 프로세스에 둔다** — 렌더러는 그리기만 한다. 창이 가려져 그리기가 느려져도 떨어지고 먹는 계산은 정확히 계속되고, 앱을 치우는 순간 진행된 상태가 그대로 보인다

## 4. 집중 판정 시스템

### 4.1 기본 원칙
**활성 창(포커스된 창) 하나만 판정한다.** 백그라운드 창은 무시.

근거:
- 유튜브를 배경에 켜놓고 작업하는 사용자를 방해로 판정하면 억울함
- 탭 여러 개를 열어둔 것은 정상 상태이지 딴짓이 아님
- 규칙이 예측 가능하고 구현이 단순함

### 4.2 앱·사이트 분류

사용자가 직접 등록. 3가지 분류.

| 분류 | exp | 스트레스 |
|---|---|---|
| 긍정 (집중) | +1/분 | −1.5/분 |
| 부정 (방해) | 0 | +1.5/분 |
| **미분류 (중립)** | **0** | **0 — 전부 정지** |

**미분류는 완전히 정지한다.** 아무것도 쌓이지 않고 아무것도 회복되지 않는다. 이걸로 3분류의 의미가 선명해진다 — **부정으로 등록한다는 건 "이건 정말 줄이고 싶다"는 의사표시**이고, 쉬려고 쓰는 앱은 미분류로 두면 된다.

> **등록 화면 안내 문구:** "정말 줄이고 싶은 것만 부정으로 등록하세요. 쉬는 시간에 쓰는 앱은 등록하지 않는 게 좋아요."

### 4.3 감지 방식

**앱 (네이티브 프로그램)**
- Windows API로 활성 창의 프로세스명 취득 (`GetForegroundWindow` → `GetWindowThreadProcessId`)
- 정확도 높음

**웹사이트**
- MVP: 활성 창 제목 문자열 매칭 (브라우저 프로세스일 때만 적용)
  - 예: 제목에 `YouTube` 포함 → 부정
- 한계: 제목이 페이지마다 바뀌어 부정확. 우회도 쉬움
- 향후: 브라우저 확장으로 URL 직접 취득 (로드맵)

### 4.4 활동 감지 — 2층 구조

**층을 나눈다.** 하나로 합치면 부정 앱에 활동 감지를 켤지 말지가 풀리지 않는다.

| 층 | 기준 | 역할 |
|---|---|---|
| **앱별 활동 감지** | 60초 무입력, 앱별 옵션 | **exp 계산용.** 코딩 중 잠깐 멈춤 처리 |
| **전역 자리 비움** | **5분 무입력 또는 앱 미실행** | **모든 분류를 무시하고 회복으로 전환** |

**앱별 활동 감지** — 사이트·앱 개별 설정으로 "활동 감지 필요" 체크박스 제공.

| 설정 | 동작 | 적합한 대상 |
|---|---|---|
| 켬 | 60초간 입력 없으면 집중 카운트 일시 정지 | 코딩, 문서 작성, 디자인 툴 |
| 끔 | 창이 활성 상태이기만 하면 카운트 | 강의 영상, 문서·논문 읽기 |

- 등록 시점에 "이 앱은 계속 입력하면서 쓰나요?"를 물어보고 기본값 설정

**전역 자리 비움** — 5분 이상 입력이 없으면 사용자가 자리에 없다고 보고, 분류와 무관하게 스트레스 회복(−20/시간)으로 넘어간다. 유튜브를 보는 동안(입력 없음)은 5분 안이라 벌점이 붙고, 자리를 뜨면 회복으로 바뀐다.

- 구현: Electron 내장 `powerMonitor.getSystemIdleTime()`

> **한계 명시:** 강의를 틀어놓고 자리를 비우는 경우는 막을 수 없다. 웹캠 등으로 막으려 하면 프라이버시 문제로 Steam 심사와 리뷰에서 더 큰 리스크가 된다. **의도적으로 막지 않는다.**

### 4.5 창 전환 처리
- **최소 체류 시간 15초**. 어떤 창에 15초 이상 머물러야 그 창의 판정이 적용됨
- 짧은 전환(알림 확인, 파일 탐색기 잠깐)으로 게이지가 요동치는 것 방지
- 15초 미만 체류는 직전 창의 판정을 유지

### 4.6 동시 실행 / 미해결 케이스
- 듀얼 모니터에서 부정 사이트를 옆에 띄워두고 보는 경우, 활성 창 기준으로는 잡히지 않음
- MVP에서는 **의도적으로 포기**. 창 가시성 판정은 로드맵으로 이월

## 5. 스트레스 / 쇠약

### 5.1 설계 원칙

**쌓은 것을 잃게 하지 않는다.** 집중 앱은 사용자가 실패했을 때에도 계속 쓰게 만들어야 성립한다. 진화 단계는 절대 되돌아가지 않는다.

**스트레스는 "오늘의 상태"다.** 며칠에 걸쳐 쌓이는 빚이 아니다. 자고 나면 씻긴다.

### 5.2 스트레스 게이지 (0~100)

| 판정 | 변화 |
|---|---|
| 긍정 앱 활성 | **−1.5/분** |
| 부정 앱 활성 | **+1.5/분** |
| 미분류 / 중립 | **0 (정지)** |
| 자리 비움 (전역 5분 무입력 또는 앱 미실행) | **−20/시간** |

**긍정과 부정을 대칭으로 맞췄다.** v0.2의 +2 / −1은 딴짓 45분을 되돌리는 데 집중 90분이 필요해서, 5.1의 "쌓은 것을 잃게 하지 않는다"와 체감이 어긋났다.

> **수치는 전부 설정 파일로 뺀다.** 플레이테스트마다 재빌드하면 튜닝이 안 된다.

### 5.3 상태 단계

| 스트레스 | 상태 | 표현 |
|---|---|---|
| 0–29 | 건강 | 발광 밝음, 촉수 유연하게 흔들림, 유영 활발 |
| 30–69 | 피로 | 발광 약해짐, 채도 빠짐, 움직임 느려짐 |
| 70–89 | 쇠약 | 발광 거의 꺼짐, 촉수 처짐, 갓이 수축, **성장 정지** |
| 90–100 | 위험 | 색이 거의 빠짐, 가라앉듯 하강, 경고 표시 |

- **70 이상에서 성장 정지가 MVP에서 스트레스의 유일한 기능적 효과다**
- 쇠약·위험 상태에서도 **집중하면 회복 가능**
- 성장은 멈추지만 진화 단계와 크기는 유지

> **플레이테스트 확인 항목 — 이중 벌점.** 딴짓하면 ①exp 안 쌓임 ②스트레스 오름 ③70 넘으면 회복하는 동안도 성장 정지. 서사상으로는 맞지만 체감이 과할 수 있다.

## 6. 하드코어 모드 — **MVP 제외, 로드맵**

**2026-09-05 결정: MVP에서 제외한다.**

**이유:** 사망 조건 하나가 스트레스 모델 전체를 결정해버린다. 스트레스가 "오늘의 상태"인지 "누적된 빚"인지가 갈리고, 그 선택이 5장 전체와 성장 시스템까지 끌고 간다. **기본으로 꺼져 있는 옵션 기능이 MVP의 핵심 시스템을 인질로 잡는 구조였다.**

### 구현 시 이미 정해둔 것

- **사망 조건:** 스트레스 90 이상(위험) 진입 후 **3일 이내에 70 미만으로 회복하지 못하면 사망.** 즉사 아님
- **"3일"은 실제 경과일**(달력 기준)이다. 집중 달성일 기준으로 하면 손 놓고 떠난 사용자는 영원히 죽지 않는다
- 유예 기간 동안 명확한 경고 UI (남은 일수 카운트다운)
- 사망 시 1단계로 리셋, 기록은 별도 보관 (최고 기록 / 역대 개체 목록)
- **모드는 개체 생성 시점에 확정되고 살아 있는 동안 바꿀 수 없다.** 양방향 모두. 바꾸려면 새 개체로 시작한다
  - 전환이 자유로우면 스트레스 92, 유예 하루 남은 상황에서 하드코어를 끄면 사망이 없던 일이 된다. 그러면 하드코어는 존재 의미가 없다
- 설정의 하드코어 항목은 **"다음 개체부터 적용"**으로 표기한다

### 구현 전 반드시 풀어야 할 충돌

현재 스트레스 모델(5.2)로는 **사망이 발동하지 않는다.** 자리 비움 −20/시간이면 8시간 자는 것만으로 −160이라 어떤 상태로 잠들어도 아침엔 0이다. 잠 회복을 막아도 90에서 70까지는 20이라 집중 14분이면 벗어난다.

검토했던 방향:
- **(A)** 사망 조건을 스트레스에서 떼어내 "3일 연속 집중 0분" 같은 직접 조건으로. 정직하고 이해하기 쉽다
- **(B)** 위험 상태에서만 잠·자리 비움 회복을 멈추고 탈출 문턱을 30까지 낮춘다
- **(C)** 일일 스트레스와 별개의 느린 "쇠약도" 축을 둔다. 표현은 풍부해지나 게이지가 둘로 늘어난다

## 7. 동작 / 모션 사양

### 7.1 상태 목록

| 상태 | 설명 |
|---|---|
| Idle | 제자리에서 갓을 수축·이완하며 부유 |
| 유영 | 화면 내 목적지로 천천히 이동 |
| 빠른 유영 | 집중 상태가 좋을 때 활발하게 이동 |
| **추격** | **먹이를 향해 곧장 이동. 빠른 유영 속도를 쓴다 (3.3)** |
| 하강 | 힘이 빠져 서서히 가라앉음 (쇠약·위험 상태) |
| 수면 | 화면 하단에서 정지, 발광 미약하게 맥동 |
| 드래그 | 마우스에 잡힌 상태, 촉수가 아래로 늘어짐 |
| 놓임 | 드래그 해제 후 관성으로 흔들리다 안정 |
| 창 가장자리 | 창 상단 모서리에 촉수를 걸고 매달림 (로드맵) |
| 반응 | 클릭 시 움찔하며 발광 |
| 진화 | 단계 상승 시 특수 연출 |

### 7.2 상태 전이 규칙
- **멈추지 않는다.** 목적지에 닿으면 곧바로 다음 자리를 잡는다. 예전엔 도착 후 4~14초 가만히 있었는데 죽은 것처럼 보였다
- 장시간 사용자 입력 없음 → 수면
- 스트레스 70 이상 → 유영 속도 감소, 하강 빈도 증가
- 각 상태는 좌우 대칭이므로 반전 처리로 방향 해결

#### 갓의 박자가 곧 헤엄이다

해파리는 갓을 오므려 물을 밀어내며 나아간다. 그러니 **모양과 이동이 같은 박자를 써야** 살아 있어 보인다. 따로 굴리면 몸은 뛰는데 엉뚱한 때 나아가는 꼴이 된다.

| 구간 | 모양 | 이동 |
|---|---|---|
| **수축** (박자의 34%) | 빠르게 오므린다 | **이때 힘이 나온다.** 확 나아간다 |
| **이완** (나머지 66%) | 천천히 편다 | 힘이 없다. 미끄러진다 |

실측하면 밀었다 미끄러졌다 하며 나아간다. 등속 직선이 아니다.

- **위로 갈 때는 이완을 짧게(34% → 52%) 하고 수축을 크게(0.20 → 0.27) 한다.** 밀어 올리는 티가 난다
- **내려갈 때는 뛰지 않고 오므린 채로 있는다.** 가라앉을 때는 힘을 쓰지 않는다. 오가는 전환은 0.4초에 걸쳐 부드럽게
- **오므릴수록 몸이 9px 내려가고 펴면 올라간다.** 제자리에서도 살아 있어 보인다
- 힘이 없는 구간에도 18%는 흐른다. 0이면 뚝뚝 끊겨 보인다
- **오므리는 정도는 0.20** — 가로 1.2배 세로 0.8배가 된다. 0.09 → 0.13 → 0.20 으로 키웠다. 작으면 뛰는지 안 뛰는지 모른다. 한 박자는 2.8초

> 박자는 메인 프로세스가 소유하고 뷰에 실어 보낸다. 계산은 `shared/stroke.ts` 한 곳에 있다.

### 7.3 창 처리

- 배경 투명, 마우스 클릭 통과(캐릭터 영역 제외)
- **멀티 모니터 자유 이동.** 해파리가 모니터 경계를 넘나들며 전체를 한 화면처럼 쓴다

#### 존재 방식 세 가지

전체화면 앱이 덮었다고 **무조건 감추지 않는다.** 그러면 전체화면으로 일하는 사용자는 제 해파리를 볼 일이 없다.

| 상태 | 창 | 언제 |
|---|---|---|
| `front` | 항상 위, 보임 | 평소 |
| **`behind`** | **always-on-top 만 해제.** 앱 뒤에 깔린다 | **사용자가 긍정으로 등록한 앱이 전체화면일 때** |
| `hidden` | 완전히 감춤 | 긍정이 아닌 앱이 전체화면일 때, 또는 사용자가 트레이에서 숨겼을 때 |

`behind` 에서는 창이 살아 있어 계속 헤엄치고 자라되 화면을 가리지 않는다. 앱을 최소화하거나 옮기면 Windows 가 알아서 드러내 주므로 별도 처리가 필요 없다.

**무엇이 긍정인지는 제품이 정하지 않는다. 사용자가 정한다** (4.2). 게임을 긍정으로 등록한 사람은 게임 중에도 해파리가 뒤에서 자라고, 등록하지 않은 사람은 감춰진다.

`hidden` 일 때는 **유영도 멈춘다.** 안 보이는 창을 계속 옮기고 다시 그릴 이유가 없다. 집중 판정과 exp 는 판정 루프가 따로 돌리므로 성장에는 영향이 없다.

#### 전체화면 판정은 "크기 일치"로 한다

덮은 비율만 보면 **바탕화면을 클릭했을 때 해파리가 사라진다.** 바탕화면 창은 모니터 세 개를 한 창으로 덮기 때문이다. 진짜 전체화면 앱은 모니터와 크기가 정확히 같고, 최대화 창은 작업 표시줄만큼 낮다는 점을 쓴다.

```
  진짜 전체화면   1920x1080   화면과 일치      -> 전체화면
  최대화 창       1936x1048   세로 3% 낮음     -> 아님
  바탕화면        3840x2160   화면의 두 배     -> 아님
```

DWM 이 감춰 둔 창(cloaked)도 제외한다. `TextInputHost` 같은 UWP 유령 창이 1920x1080 으로 잡히기 때문이다.

**해파리가 지금 있는 모니터만 본다.** 다른 모니터의 전체화면 게임 때문에 숨으면 버그다

#### 자유 이동의 필수 구현 제약

모니터 배치가 L자·계단형이면 **가상 데스크톱 경계 사각형 안에 실제 모니터가 없는 빈 구역이 생긴다.** 해파리가 가상 영역 기준으로 유영하면 그 구역으로 흘러들어가 완전히 사라진다.

1. **유효 영역 = 실제 디스플레이 사각형들의 합집합.** 가상 데스크톱 경계 사각형 금지
2. 목적지 샘플링과 **이동 경로 중간점** 모두 합집합 안에 있는지 검사
3. 서로 붙어 있지 않은 모니터 사이는 **경유 모니터를 거치는 인접 그래프**로 경로를 잡는다
4. `display-removed` · `display-metrics-changed` 이벤트에서 화면 밖 좌표를 구조
5. 트레이 메뉴에 **"해파리 불러오기"** — 현재 활성 창이 있는 모니터 중앙으로 소환
6. 창 이동 시 `screen.getDisplayNearestPoint()`의 `scaleFactor`로 렌더 크기 보정

> **혼합 DPI 주의.** 개발 환경 3대가 전부 1920x1080 동일 배율이라 혼합 DPI를 재현할 수 없다. 노트북 150% + 외부 모니터 100% 조합은 흔하다. **Windows 디스플레이 설정에서 모니터 하나의 배율만 125%/150%로 임시 변경해 수동 테스트하고, 릴리스 전 체크리스트에 넣는다.**

## 9. 기술 스택

### 9.1 프레임워크 — **Electron 확정**

**결정 근거 1 — 같은 기술 영역의 검증된 코드베이스가 이미 있다.**

`blackhole-trash`(Windows 11 always-on-top 투명 데스크톱 위젯, Electron 43 + TS + esbuild + koffi)에 9.2가 요구하는 네이티브 기능층이 대부분 구현돼 있다.

| 요구사항 | blackhole-trash 현황 |
|---|---|
| 활성 창 프로세스명 취득 | `src/native/win32/windows.ts`에 `GetWindowThreadProcessId` 이미 선언 |
| 마지막 입력 시각 (idle) | Electron 내장 `powerMonitor.getSystemIdleTime()` |
| 투명창 + always-on-top + 클릭 통과 | `src/main/window.ts` |
| 캐릭터 영역만 클릭 받기 | `src/main/cursor-watch.ts` |
| 멀티 모니터 | `src/main/desktop/stage/rescue.ts` |

특히 **Electron 최대의 실무 함정인 네이티브 모듈 재빌드 문제를 이미 밟고 해결책(koffi)까지 확보한 상태**다. `ffi-napi`는 Electron 21 이상에서 동작하지 않는다.

**결정 근거 2 — 메모리 격차를 실측했다.**

blackhole-trash 실행 25초 후 Private Working Set 합계 **85.1 MB** (main 24.8 / renderer 7.0 / gpu 23.0 / utility 30.3). 60fps 애니메이션을 계속 돌리는 최적화 전 상태에서 나온 값이다. Tauri로 같은 걸 만들면 40~60MB이니 격차는 30MB 안팎. 같은 트레이에 상주하는 Discord가 300MB 이상을 쓴다.

**WPF는 탈락.** Spine이든 Rive든 웹 런타임을 쓰므로 WebView가 필요하다.

#### 비기능 요구사항 — 상주 메모리 130MB 이하

- **목표: Private Working Set 합계 130MB 이하** (측정 기준 = 작업 관리자 표시값)
- **측정은 실행 60초 이후 안정 상태에서 한다.** 20초 시점은 힙이 차기 전이라 실제보다 15MB 쯤 낮게 나온다. 처음 이 예산을 100MB 로 잡을 때 근거로 삼은 83~87MB 가 그 함정에 걸린 값이었다
- 값이 오르내리는 것은 정상이다. GC 주기 때문에 톱니 모양으로 ±5MB 진동한다. 평균과 최댓값을 함께 본다
- 초과 시 최적화를 강제한다:
  - 렌더러 프로세스 1개 유지 (창 추가 시 재사용)
  - `backgroundThrottling` 활성 + 수면 상태에서 애니메이션 프레임 정지
  - 전체화면 앱 감지로 숨김일 때 렌더링 중단
  - 통계·설정 창은 필요할 때 열고 닫으면 파기 (상주 금지)
- MVP 완료 시점과 스토어 출시 직전에 각각 재측정해 기록한다

### 9.2 필요 네이티브 기능
- 활성 창 프로세스명·제목 취득 (`GetForegroundWindow` + `GetWindowThreadProcessId`, koffi)
- 마지막 입력 시각 (`powerMonitor.getSystemIdleTime()`)
- 전체화면 앱 감지
- 창 위치·크기 취득 (창 가장자리 매달리기용 — 로드맵)
- 시작 프로그램 등록

### 9.3 Steam 연동
- Steamworks SDK (도전과제, 클라우드 세이브)
- 도전과제 예시: 첫 진화, 완성체 도달, 7일 연속 목표 달성
- (하드코어 완성 도전과제는 로드맵)

### 9.4 저장 데이터

- 앱·사이트 분류 목록

- **밸런싱 수치는 별도 설정 파일로 분리** (재빌드 없이 튜닝)

## 10. 프라이버시

Steam 스토어 페이지에 데이터 수집 항목 고지 필요.

- 활성 창의 프로세스명과 창 제목을 **읽지만 저장하지 않는다**
- 저장하는 것은 매칭 결과(긍정/부정/중립)와 시간뿐
- 키 입력 내용은 읽지 않음. 입력이 **있었는지 여부**만 확인
- **외부 전송은 Steam 클라우드 세이브뿐이다.** 그 외 네트워크 통신은 없다
  - Steam 클라우드로 올라가는 것: 캐릭터 상태, 앱·사이트 분류 목록, 설정값, 일별 집중 기록
  - 자체 서버는 없다
- 설정 화면과 최초 실행 시 위 내용을 명시

## 12. MVP 범위

### 포함
- 해파리 1종, 5단계 진화
- 활성 창 기반 집중 판정 (프로세스명 + 창 제목 매칭)
- 활동 감지 2층 구조 (앱별 60초 + 전역 5분)
- 스트레스/쇠약 시스템 (하루 지표)
- 멀티 모니터 자유 이동
- **먹이 (3.3)** — 집중 중 낙하, 추격, 먹기
- 기본 모션 (Idle, 유영, 추격, 수면, 드래그, 반응)
- 트레이 + 설정 + 간단한 통계

### 제외 (로드맵)
- **하드코어 모드** — 2026-09-05 이관
- 브라우저 확장을 통한 정확한 URL 판정
- 창 가시성 판정 (듀얼 모니터 대응)
- 다중 캐릭터 / 다른 종 추가
- 커스터마이징 (색상, 무늬)
- macOS 지원
- 창 가장자리 매달리기 (구현 난이도 높음)
