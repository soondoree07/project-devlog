결정된 항목은 기획서 본문에 반영하고, 여기에는 **왜 그렇게 정했는지**를 남긴다.

## 1. 애니메이션 툴 — 보류 (시안 대기)

**상태:** 미정. 해파리 그림체 시안을 두 방향으로 만들어 비교한 뒤 결정.

**기획서의 오류를 먼저 정정함.** 기획서 2.3에 적힌 "Spine 개인 라이선스 $69"는 Essential
등급이고, 여기엔 **메시(mesh)·웨이트·IK가 빠져 있다.** 뼈 회전만 된다. 해파리는 갓의
수축·이완과 촉수의 흐느적거림이 핵심 모션이라 메시 변형 없이는 만들 수 없다.
실제로 필요한 등급은 **Spine Professional $369**.

**후보 3종 비교**

| | Spine Pro | DragonBones | Rive |
|---|---|---|---|
| 비용 | $369 영구 | 무료 | 무료 티어 + 상용 출시 시 $9/월(연납) |
| 메시 변형 | 포함 | 포함 | 포함 (무료 티어부터) |
| 상태 머신 | 없음 (코드로 직접) | 없음 | **내장** |
| 런타임 | 상용, 웹 런타임 있음 | 커뮤니티 유지 | 오픈소스·무료, 런타임 수수료 없음 |
| 유지보수 | 활발 | 사실상 중단 (Egret) | 활발 |
| 화풍 궁합 | 그림 파츠(수채·텍스처) 강함 | 그림 파츠 | 벡터 우선 — 텍스처 회화체 불리 |

**Rive가 유력한 이유는 가격이 아니라 상태 머신이다.** 기획서 7.1에 상태 10종, 7.2에
전이 규칙이 이미 그래프로 설계돼 있다. Rive는 이 그래프를 툴 안에서 만들고 앱에서는
`stress`·`stage` 같은 입력값만 던지면 된다. Spine이면 전이 로직을 전부 코드로 짜고
유지해야 하고, 여기에 5단계 × 4스트레스 변형이 곱해진다.

**갈림길은 화풍이다.** 깔끔한 반투명 발광 → Rive. 수채·텍스처가 살아있는 회화체 → Spine Pro.
기획서 2.2가 "일러스트 기반"이라고만 해서 이 부분이 비어 있다.

**DragonBones는 권하지 않는다.** 유료로 파는 상주 프로그램의 렌더링 심장부를
유지보수가 끊긴 런타임에 맡기는 위험이 크다.

**다음 액션:** 두 방향 해파리 시안 생성 → 눈으로 비교 → 툴 확정.

## 2. 프레임워크 — **Electron 확정** (+ 메모리 예산 100MB)

**결정일:** 2026-09-05

**근거 1 — 같은 기술 영역의 검증된 코드베이스가 이미 있다.**
`blackhole-trash`(Windows 11 always-on-top 투명 데스크톱 위젯, Electron 43 + TS + esbuild + koffi)에
Jellum 9.2가 요구하는 네이티브 기능층이 대부분 구현돼 있다.

| Jellum 9.2 요구사항 | blackhole-trash 현황 |
|---|---|
| 활성 창 프로세스명 취득 | `src/native/win32/windows.ts`에 `GetWindowThreadProcessId` 이미 선언 (`GetForegroundWindow`만 추가) |
| 마지막 입력 시각 (idle) | Electron 내장 `powerMonitor.getSystemIdleTime()`으로 `GetLastInputInfo` 없이 해결 |
| 투명창 + always-on-top + 클릭 통과 | `src/main/window.ts` — `transparent`·`skipTaskbar`·`setIgnoreMouseEvents(true,{forward:true})` |
| 캐릭터 영역만 클릭 받기 | `src/main/cursor-watch.ts` — 이미 푼 문제 |
| 멀티 모니터 | `src/main/desktop/stage/rescue.ts`에서 `screen.getAllDisplays()` 사용 |

특히 `src/native/win32/index.ts` 주석 — *"ffi-napi는 Electron 21 이상에서 동작하지 않아
쓸 수 없다. koffi는 프리빌트 바이너리를..."* — Electron 최대의 실무 함정인
**네이티브 모듈 재빌드 문제를 이미 밟고 해결책까지 확보한 상태**다.

**근거 2 — 메모리 격차를 실측했고, 감수할 만하다.**
blackhole-trash 실행 25초 후 측정 (2026-09-05):

| 프로세스 | Private Working Set |
|---|---|
| main | 24.8 MB |
| renderer | 7.0 MB |
| gpu-process | 23.0 MB |
| utility | 30.3 MB |
| **합계 (작업 관리자 표시값)** | **85.1 MB** |

> Working Set 총합은 679MB로 나오지만 Chromium 바이너리가 프로세스마다 중복 계산된
> 값이라 실제 점유가 아니다. 사용자가 작업 관리자에서 보는 숫자는 85MB다.

이건 불리한 조건에서 나온 값이다 — blackhole-trash는 복제본을 60fps로 계속 돌리므로
유영하는 해파리와 부하 성격이 같고, 최적화 전 상태다. Tauri로 같은 걸 만들면 대략
40~60MB이니 격차는 **30MB 안팎**. 같은 트레이에 상주하는 Discord가 300MB 이상,
Steam 클라이언트 자체가 300MB 이상을 쓴다.

**30MB를 아끼려고 검증된 win32 계층·히트테스트·멀티모니터 코드를 버리고 Rust를 새로
배우는 것은 손해다.**

**WPF는 자동 탈락.** Spine이든 Rive든 웹 런타임을 쓰므로 WebView가 필요하다.

### 부수 결정 — 비기능 요구사항: 상주 메모리 100MB 이하

기획서 9.1이 지적한 "메모리가 리뷰에 직결된다"는 우려를 숫자로 못 박아 관리한다.

- **목표: Private Working Set 합계 100MB 이하** (측정 기준 = 작업 관리자 표시값)
- 초과 시 최적화를 강제한다. 후보 수단:
  - 렌더러 프로세스 1개 유지 (창 추가 시 재사용)
  - `backgroundThrottling` 활성 + 수면 상태에서 애니메이션 프레임 정지
  - 전체화면 앱 감지로 숨김일 때 렌더링 중단
  - 통계·설정 창은 필요할 때 열고 닫으면 파기 (상주 금지)
- MVP 완료 시점과 스토어 출시 직전에 각각 재측정해 기록한다.

## 3. 일일 경험치 상한 — **소프트 캡 확정** (1:1 구간 5시간, 초과분 1/10, 총량 3,600 유지)

**결정일:** 2026-09-05

### 확정 규칙

- **집중 1분 = 1 exp** (기획서 3.3 그대로)
- **하루 300분(5시간)까지는 1:1로 인정**
- **300분 초과분은 1/10만 인정** — 하드 상한 없음
- **1일치 = 120 exp**, 완성까지 **총 3,600 exp** (= 30일치) 유지
- 이 기준선 300분은 **전역 고정값**이다. 사용자가 바꿀 수 없다.
- 사용자 설정 일일 목표(기본 120분)는 **성장 계산에서 분리한다.** 목표는
  "오늘 해냈다" 표시와 스트레스 판정에만 쓴다.

### 사용자 유형별 완성 기간

| 하루 집중 | 완성 |
|---|---|
| 60분 | 60일 |
| 120분 (기본 목표) | **30일** |
| 180분 | 20일 |
| 300분 (5시간) | 12일 |
| 주말만 각 5시간 | 42일 |

### 왜 이렇게 정했나

**초안(일일 상한 1.0일치)에는 구조적 문제가 있었다.** 부분 인정(60분=0.5일치)과 상한을
같이 쓰면 총 집중 시간이 같아도 편차가 큰 사람이 손해를 본다. 상한은 넘치는 날만 자르고
부족한 날은 채워주지 않아 편차가 언제나 벌점으로만 작용한다.

| 패턴 (모두 평균 120분/일) | 초안 상한 1.0 적용 시 |
|---|---|
| 매일 120분 | 30일 |
| 60분 / 180분 번갈아 | 40일 |
| 평일 0분, 주말 각 420분 | **105일** |

세 번째가 학생·직장인의 실제 패턴인데 105일이 걸린다. 4.2에서 목표를 조절 가능하게 만들어
편차를 흡수하려 했는데, 상한이 그 편차를 다시 벌점으로 되돌려놓는 구조였다.

**1:1 구간을 5시간으로 넓혀 이 문제를 해결했다.** 주말형이 105일 → 42일로 내려온다.

### 같이 막은 구멍 — 소프트 캡 기준선의 전역 고정

기준선을 **사용자 설정 목표**로 두면 설정 한 번으로 캡이 무력화된다.

- 목표 120분 설정 → 하루 240분 집중 → 132 exp
- 목표 **240분** 설정 → 하루 240분 집중 → **240 exp** (같은 시간인데 1.8배)
- 목표 480분 설정 → 하루 480분 집중 → **7.5일 완성**

반대로 3.3의 "완성까지 총 3,600 exp"가 목표에 연동되는지 고정인지도 명시가 없어서,
목표를 10분으로 낮추면 총 5시간 만에 완성되는 해석도 가능했다.
**기준선을 전역 고정 300분으로 못 박아 양쪽을 다 막았다.**

### 감수하기로 한 것

- **소프트 캡은 사실상 거의 작동하지 않는다.** 하루 5시간을 순수 집중으로 넘기는
  사용자가 극소수라 1/10 규칙이 걸리는 일이 드물다. 실질적으로 "상한 없음"에 가깝다.
- **5시간형은 12일에 완성한다.** 총 집중 60시간으로 2시간형 30일과 정확히 같으므로
  노력 대비로는 공정하다고 보고 받아들인다.
- 콘텐츠 소진은 3.1에 이미 있는 **완성체 이후 크기 미세 증가**와
  **"며칠째 키우는 중" 카운터**로 받친다.

**총량을 3,600에서 올리지 않은 이유:** 진화표(3·8·15·30일차)의 뼈대가 무너진다.
총량을 4,500으로 올리면 가장 흔한 2시간 사용자가 37일로 늘어지면서 4단계 15일 구간이
19일로 벌어지는데, 기획서 3.1이 "여기가 비면 이탈한다"고 스스로 경고한 구간이다.

## 4. 멀티 모니터 간 이동 — **자유 이동 허용** (유효 영역 판정 필수)

**결정일:** 2026-09-05

해파리가 모니터 경계를 넘나들며 전체를 한 화면처럼 쓴다.

### 실측한 개발 환경 (2026-09-05)

```
       (0,-1080)
       ┌──────────┐
       │ DISPLAY1 │      ← 빈 공간 (모니터 없음)
       └──────────┘         (1920,-1080) ~ (3840,0)
(0,0)  ┌──────────┬──────────┐
       │ DISPLAY2 │ DISPLAY3 │
       │ primary  │          │
       └──────────┴──────────┘
                          (3840,1080)
```

| 디스플레이 | 위치 | 크기 | 주 모니터 |
|---|---|---|---|
| DISPLAY1 | (0, −1080) | 1920x1080 | |
| DISPLAY2 | (0, 0) | 1920x1080 | O |
| DISPLAY3 | (1920, 0) | 1920x1080 | |

가상 데스크톱: (0, −1080)에서 3840x2160

### 반드시 지켜야 할 구현 제약

**L자 배치라 가상 데스크톱 경계 사각형에 빈 구역이 생긴다.**
오른쪽 위 (1920,−1080)~(3840,0)에는 모니터가 없다. 해파리가 가상 영역 기준으로
유영하면 이 구역으로 흘러들어가 **완전히 사라진다.** 이 배치에서는 반드시 일어난다.

1. **유효 영역 = 실제 디스플레이 사각형들의 합집합.** 가상 데스크톱 경계 사각형 금지
2. 목적지 샘플링과 **이동 경로 중간점** 모두 합집합 안에 있는지 검사
3. DISPLAY1(위)과 DISPLAY3(오른쪽)은 인접하지 않으므로 **DISPLAY2를 경유**하는
   모니터 인접 그래프를 따라 경로를 잡는다
4. `display-removed` · `display-metrics-changed` 이벤트에서 화면 밖 좌표를 구조
   (blackhole-trash `src/main/desktop/stage/rescue.ts`와 같은 발상)
5. 트레이 메뉴에 **"해파리 불러오기"** — 자유 이동일수록 더 필요하다.
   현재 활성 창이 있는 모니터 중앙으로 소환
6. 7.3 전체화면 앱 감지는 **해파리가 지금 있는 모니터 기준**으로 판정.
   다른 모니터의 전체화면 게임 때문에 숨으면 버그다

### 감수하기로 한 위험 — 혼합 DPI

개발 환경 3대가 전부 1920x1080 동일 배율이라 **혼합 DPI를 재현할 수 없다.**
노트북 150% + 외부 모니터 100% 조합은 흔하고, 배율이 다른 모니터로 창을 옮길 때
크기가 튀는 것은 Electron의 고질적 함정이다. 개발자가 못 잡는 버그가 출시될 수 있다.

**대응:** Windows 디스플레이 설정에서 모니터 하나의 배율만 125%/150%로 임시 변경해
수동 테스트하는 절차를 문서화하고, 릴리스 전 체크리스트에 넣는다.
창 이동 시 `screen.getDisplayNearestPoint()`의 `scaleFactor`를 읽어 렌더 크기를 보정한다.

## 5. 하드코어 ↔ 일반 모드 전환 — **전환 불가, 개체 단위 고정** (MVP 제외로 보류)

**결정일:** 2026-09-05
**2026-09-05 갱신: 하드코어 모드 자체를 MVP에서 제외했다.** 아래 결정은 하드코어를
로드맵에서 구현할 때 그대로 적용한다. MVP에는 들어가지 않는다.

- **모드는 개체 생성 시점에 확정되고, 살아 있는 동안 바꿀 수 없다.** 양방향 모두.
- 모드를 바꾸려면 새 개체로 시작해야 한다 (현재 개체를 포기하는 선택).
- 하드코어 사망으로 1단계 리셋될 때 모드를 다시 고를 수 있다.
- **기획서 8.3 수정 필요:** 설정의 "하드코어 on/off"는 **"다음 개체부터 적용"**으로 바꾼다.
  진행 중에는 못 바꾸므로 현재 개체에 영향이 없다는 걸 UI에서 분명히 해야 한다.

**왜 이렇게 정했나 — 도망을 막는다.**
전환이 자유로우면 스트레스 92, 유예 하루 남은 상황에서 설정을 열어 하드코어를 끄면
사망이 없던 일이 된다. 그러면 하드코어는 존재 의미가 없다. 위험할 때만 끄면 되니까.

### 5-1. 사망 유예 "3일"의 기준 — **실제 경과일** (기획서 6장 공백 메움)

성장의 "1일차"는 집중 목표 달성일(3.2)이지만, **사망 유예는 달력 기준 3일이다.**
집중 달성일 기준으로 하면 손 놓고 떠난 사용자는 영원히 죽지 않아 사망 조건 자체가
유명무실해진다.

### 5-2. 같이 막은 구멍 — 앱을 꺼서 도망가기

5.2에 "중립/미사용은 시간당 −5"가 있다. 유예를 실제 경과일로 세면서 앱이 꺼진 동안에도
이 회복을 적용하면, **위험 상태에서 앱을 끄는 것이 최선의 전략이 된다.**
3일이면 −360이라 무조건 0으로 회복된다. 죽기는커녕 완치된다.

**규칙:** 하드코어 모드에서 **위험 상태(스트레스 90+)에 진입한 순간부터, 앱이 꺼져 있던
시간은 회복에 산입하지 않는다.** 유예 카운트다운에만 산입한다. 위험에 빠지면 실제로
집중해야만 빠져나올 수 있다.

일반 모드는 사망이 없으므로 미사용 회복을 그대로 적용한다 (5.1 원칙에 부합).

## 8. 스트레스 밸런싱 — **모델 확정** (하루 지표, 중립 정지, ±1.5 대칭)

**결정일:** 2026-09-05

### 확정 모델

| 판정 | exp | 스트레스 |
|---|---|---|
| 긍정 앱 활성 | +1/분 | −1.5/분 |
| 부정 앱 활성 | 0 | +1.5/분 |
| **미분류 / 중립** | **0** | **0 — 전부 정지** |
| **자리 비움** (전역 5분 무입력 또는 앱 미실행) | 0 | **−20/시간** |

- **스트레스는 "오늘의 상태"다.** 자고 나면 씻긴다. 며칠에 걸쳐 쌓이는 빚이 아니다.
- 상태 단계(5.3)는 표현용으로 유지: 0–29 건강 / 30–69 피로 / 70–89 쇠약 / 90–100 위험
- 70 이상에서 성장 정지는 유지. **MVP에서 스트레스의 유일한 기능적 효과다.**
- **수치는 전부 설정 파일로 뺀다.** 플레이테스트마다 재빌드하면 튜닝이 안 된다.

### 중립을 완전히 정지시킨 이유

초안 5.2의 "중립/미사용 시간당 −5"를 없앴다. **3분류의 의미가 선명해진다.**
부정으로 등록한다는 건 "이건 정말 줄이고 싶다"는 의사표시고, 쉬려고 쓰는 앱은
미분류로 두면 된다.

이걸로 **초안의 휴식 문제가 사용자 손에서 해결된다.** 초안대로 분당 +2였다면
점심시간에 40분짜리 영상 하나로 건강에서 위험까지 직행했다. 뽀모도로의 절반은
휴식인데 집중 앱이 정당한 휴식을 벌점으로 처리하는 셈이었다.

> **등록 화면에 안내한다:** "정말 줄이고 싶은 것만 부정으로 등록하세요.
> 쉬는 시간에 쓰는 앱은 등록하지 않는 게 좋아요."

### "자리 비움"은 분류와 다른 축이다

중립과 함께 없애면 스트레스가 영원히 안 내려간다. 어제 80을 쌓고 오늘 중립 앱만
쓰면 계속 80이다. **자리 비움은 별개 축으로 남긴다.**

판정을 두 층으로 나눈다.

| 층 | 기준 | 역할 |
|---|---|---|
| 앱별 활동 감지 (기획서 4.4) | 60초 무입력, 앱별 옵션 | **exp 계산용** — 코딩 중 잠깐 멈춤 처리 |
| **전역 자리 비움** | **5분 무입력 또는 앱 미실행** | **모든 분류를 무시하고 회복으로 전환** |

이렇게 나누면 부정 앱에 활동 감지를 켤지 고민할 필요가 없다. 유튜브를 보는 동안
(입력 없음)은 5분 안이라 벌점이 붙고, 자리를 뜨면 회복으로 바뀐다.

### ±1.5 대칭으로 맞춘 이유

초안의 +2 / −1은 **딴짓 45분을 되돌리는 데 집중 90분**이 필요했다.
5.1의 "쌓은 것을 잃게 하지 않는다"와 체감이 어긋난다.

### 하드코어를 빼서 풀린 문제

이 모델은 하드코어가 MVP에 있는 한 성립하지 않았다. 두 문제가 있었다.

**문제 1 — 사망이 사실상 불가능했다.** 자리 비움 −20/시간이면 8시간 자는 것만으로
−160이다. 어떤 상태로 잠들어도 아침엔 0이라, 6장의 "위험 진입 후 3일 이내 70 미만
회복 실패 시 사망"이 자면 자동 해제돼 발동할 수 없었다.

**문제 2 — 위험 탈출이 너무 쌌다.** 잠 회복을 막아도 90에서 70까지는 20이라
집중 14분이면 벗어난다. 3일 유예 동안 14분을 못 내는 사람은 앱을 아예 안 켜는
사람뿐이라, 사망 조건이 실질적으로 "3일 동안 앱을 안 켰다"와 같아졌다.

**근본 원인은 스트레스의 정체가 안 정해진 것이었다.** 기획서 5장은 "오늘의 상태"로,
6장은 "누적된 빚"으로 쓰였다. **하드코어를 MVP에서 빼면서 "오늘의 상태"로 확정했다.**

> 하드코어를 로드맵에서 구현할 때 이 충돌을 다시 풀어야 한다. 당시 검토한 방향:
> **(A)** 사망 조건을 스트레스에서 떼어내 "3일 연속 집중 0분" 같은 직접 조건으로 —
> 정직하고 이해하기 쉽다. **(B)** 위험 상태에서만 잠·자리 비움 회복을 멈추고
> 탈출 문턱을 30까지 낮춘다. **(C)** 일일 스트레스와 별개의 느린 "쇠약도" 축을 둔다 —
> 표현은 풍부해지나 게이지가 둘로 늘어난다.

### 남은 튜닝 대상

- **이중 벌점 여부.** 딴짓하면 ①exp 안 쌓임 ②스트레스 오름 ③70 넘으면 회복하는
  동안도 성장 정지. 서사상으로는 맞지만 체감이 과할 수 있다. 플레이테스트 항목.
- 자리 비움 −20/시간이 적정한지 (8시간 수면 = −160, 사실상 무조건 0)
- 성장 정지 임계값 70이 적정한지

## 기획서를 읽고 발견한 쟁점 (미결정 8건과 별개)

### A. 프라이버시 문구 충돌 — 10장 vs 9.3 — **해결**

10장은 "외부 서버 전송 없음"인데 9.3에 Steam 클라우드 세이브가 있었다. 세이브 동기화는
Valve 서버로 나가는 전송이다. 그대로 두면 스토어 데이터 수집 고지와 실제 동작이 어긋난다.

**조치:** 10장 문구를 **"Steam 클라우드 외 외부 전송 없음"**으로 수정. 무엇이 Steam
클라우드로 올라가는지(캐릭터 상태·설정·일별 집중 기록)도 함께 명시한다.

### B. 하드코어 "3일"의 단위 — **해결 후 보류**

성장의 "1일차"는 집중 목표 달성일인데 사망 유예 3일은 실제 경과일로 읽혔다.
**실제 경과일로 확정**했으나, 하드코어가 MVP에서 빠지면서 로드맵으로 이월됐다. 5번 참조.

### C. 스트레스 회복이 축적보다 2배 느림 — 5.2 — **해결**

부정 +2 / 긍정 −1이라 유튜브 45분을 되돌리는 데 집중 90분이 필요했다.
**±1.5 대칭으로 수정.** 8번 참조.

### D. 부분 인정과 일일 상한의 조합 — 3.2 — **해결**

편차가 있는 사용자가 구조적으로 손해를 보는 구조였다(주말형 105일).
**1:1 인정 구간을 5시간으로 넓혀 해결.** 3번 참조.
